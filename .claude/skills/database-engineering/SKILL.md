# Database Engineering

## When to use
Adding/changing tables or columns, writing migrations, vector or keyword search indexes, repositories, or diagnosing slow queries.

## Required project context
`brain/DATABASE_SCHEMA.md` (Proposed), `docs/backend/DATABASE_DESIGN.md`. Reality: no models, no Alembic init, `migrations/versions/` empty. `EMBEDDING_DIM=1024` default ties vector columns to the (still Unknown) embedding model. asyncpg and psycopg are both in requirements.

## Engineering principles
- The schema encodes business rules (constraints, uniqueness, FKs).
- Migrations are reviewed, reversible where feasible, never edited after applied.
- Repositories own SQL and enforce owner scoping.
- Test against real PostgreSQL with pgvector, never SQLite.
- Never run migrations on a real database without explicit approval.

## Workflow
1. Read the proposed schema and the feature need; adjust the design and update `DATABASE_SCHEMA.md` to match what you will build.
2. Create/extend models (`Mapped[...]`, naming convention, UUID pks, timestamptz).
3. Generate a migration draft, then hand-review it: extension creation, types, indexes, FKs with `ON DELETE`.
4. Add repository methods taking owner id where applicable.
5. On a throwaway database: `upgrade head` → `downgrade base` → `upgrade head`.
6. `EXPLAIN` hot queries (vector search with jurisdiction/date filter, keyword search).
7. Update docs; record notable decisions (e.g. role of psycopg, enum strategy).

## Relevant files
`backend/app/models/`, `backend/app/repositories/`, `backend/migrations/`, `backend/app/core/config.py`.

## Implementation requirements
- Index every FK and frequent filter column. HNSW with the operator class matching the query distance. GIN on `tsvector`.
- Store the embedding model id per chunk.
- Uploads carry `expires_at`; erasure paths delete rows and files.
- No transaction held across NVIDIA calls or file parsing.

## Testing requirements
Migration up/down/up in CI; repository tests including cross-user isolation; constraint-violation tests; a vector search ordering test on a tiny fixed fictional corpus.

## Common mistakes
- Changing `EMBEDDING_DIM` without a migration and re-embed.
- Autogenerated migration committed unreviewed.
- Missing index on foreign keys; unbounded `SELECT`s.
- Committing inside repositories.
- Putting file bytes in the database.

## Definition of done
Models, migration, repositories and tests in place; up/down verified on a throwaway DB; indexes justified; schema docs match what is migrated.
